# SRS 仕様

## この文書の役割

- incubate 構想（incubate仕様.md / incubate哲学.md）を引き継ぎ、対話で練り直した結果をまとめたもの
- 2026-06-30 の対話で方向が固まった
- Status: Draft（`srs/vault-wide` ブランチで実装・テスト済み、実運用で検証中）
- **main ブランチには未実装。** `srsGrowthEnabled` 設定も成長ロジックも main のコードには存在しない。実装（vault-wide 方式）とテスト（`tests/srs-completion.test.ts` ほか）は `srs/vault-wide` ブランチにある

## 何をするか

`repeat > 0` を持つノートを完了すると、repeat の間隔が自動で広がっていく仕組み。暗記カードのような細かい評価（hard / good / easy）はしない。チェックしたら伸びる、それだけ。

## 使い方

1. 設定画面の SRS セクションで「SRS 成長（実験的）」を ON にする（デフォルト OFF）
2. 繰り返し見たいノートの frontmatter に `repeat: 1` を書く。置き場所は vault 内のどこでもよい（routine/ 配下だけは対象外）
3. デイリーノートのルーチン挿入に、その日 due の SRS ノートが末尾に並ぶ（1日の件数は `srsMaxDaily`、デフォルト3件まで）
4. チェックを付けて完了すると、`next_due` が先送りされ、`repeat` が 2〜3 倍に育つ。繰り返すほど出てくる間隔が開いていく

やめたいノートは `repeat` を消すか 0 にする。毎日やりたくなったノートは routine/ フォルダに移す（その際 repeat の値は手で直す。「routine/ に移動したとき」を参照）。

## 設定

`srsGrowthEnabled`（デフォルト OFF）。設定画面で「SRS growth（実験的）」としてトグルを出す。OFF のとき SRS の成長処理は一切走らない。routine/ のノートはこの設定に関係なく今まで通り動く。

## 対象ノートの判定（vault-wide 方式）

以下の条件をすべて満たすノートが SRS 対象になる：

- `srsGrowthEnabled` が ON
- routine/ フォルダ配下にない（サブフォルダも含めて除外。routine/完了/ のようなフォルダも対象外）
- YAML の `repeat` が 0 より大きい数値

srs/ フォルダに入っている必要はない。vault のどこにあっても `repeat > 0` なら対象になる。routine/ 配下だけが例外で、こちらは repeat があっても SRS 成長しない従来の動作を維持する。

`repeat: 0` にするか、repeat フィールドを消すと SRS 対象から外れる。routine/ に移動しても外れる。

### folder-based 方式（廃案）

srs/ フォルダに入っているノートだけを SRS 対象にする方式も別ブランチで試したが、vault-wide 方式を採用して比較用ブランチは削除済み。ノートを特定フォルダに集める必要がなく、`repeat` の有無だけで出し入れできる点を取った。

## incubate 構想からの変更点

incubate 構想では `@x` / `@hard` マーカーで「間隔を縮める」操作を想定していた。SRS ではそれをやらない。「明日もやりたい」と思ったら routine/ にノートを手で移動する。間隔の調整は仕組みではなく、フォルダ移動というアナログな判断で行う。

incubate 構想では growth rate をプラグイン設定で管理し、jitter や max interval も設定項目として想定していた。SRS の初期実装ではこれらは全部なし。growth rate は 2〜3 の乱数で固定。

incubate という名前は SRS に変わった。

## 完了時の動作

SRS 対象のノートを完了すると：

1. 現在の repeat を取得する（未設定なら 1、0 なら 1 として扱う）
2. next_due を completionDay + 現在の repeat で更新する（completionDay はデイリーノートの日付）
3. 成長の基準値を決める（後述の overdue growth を参照）
4. 基準値に 2〜3 の乱数をかけて、整数に丸める
5. repeat を新しい値で書き戻す

next_due の計算には成長前の repeat を使う。成長後の repeat は次回の完了時に使われる。

routine/ フォルダのノートは今まで通り。repeat は伸びない。

## Overdue growth（期限超過時の成長）

期限を過ぎてから完了した場合、経過日数が現在の repeat より長ければ、経過日数を成長の基準値に使う。

例: repeat: 3 のノートが 6月20日 due で、6月30日に完了した場合。経過日数は 10日で、repeat の 3 より大きい。10 を基準にして 2〜3 倍すると、次の repeat は 20〜30 になる。

期限内に完了した場合、あるいは next_due が設定されていない場合は、現在の repeat がそのまま基準値になる。

根拠: 期限より遅れて完了しても内容を覚えていたなら、その期間分の記憶の持続力がある。SM-2 / Anki と同じ考え方で、長く覚えていた分だけ次の間隔を広げる。

## 成長の感覚

growth rate は 2〜3 の乱数。repeat: 1 から始めた場合の推移（中央値での例）：

repeat: 1 から始めた場合（next_due は成長前の repeat で決まり、repeat は完了後に育つ）：

- 1回目完了: 1日後に出る。repeat が 2〜3 に育つ
- 2回目完了: 2〜3日後に出る。repeat が 4〜9 に育つ
- 3回目完了: 4〜9日後に出る。repeat が 8〜27 に育つ
- 4回目完了: 8〜27日後に出る。repeat が 16〜81 に育つ

4回チェックすれば週1〜月1以上の頻度まで開く。振り返りレベルの雑さで回す運用に合っている。

## YAML

routine と同じ YAML をそのまま使う。SRS 専用のフィールドは追加しない。

```yaml
---
repeat: 1
next_due: 2026-06-30
---
```

start, estimate, section, start_before, summary_role もそのまま使える。SRS 完了時にこれらのフィールドは触らない。

## routine/ に移動したとき

SRS 対象のノートを routine/ に移動すると、repeat が成長済みの値（例: 20）のまま残る。routine 側では repeat: 20 は「20日ごと」として動くので、毎日やりたいなら手で repeat: 1 に直す必要がある。当面はこれを許容する。

## ノートの分類と整理

srs/ フォルダはフラットに使う。サブフォルダは作らない。

142件中117件が本の振り返りで残り25件がそれ以外だが、日次の運用ではその日 due のものだけ出てくるので、フォルダ内の見通しが問題になる場面は少ない。一覧が必要なときは Dataview（`_SRSタスク一覧.base` など）で作る。

将来、分類が必要になった場合はサブフォルダ（srs/本/ など）の方向で考えている。タグで分類する方法もあるが、「SRS をやめる」操作がタグを消すよりフォルダから出す方が直感的で、消し忘れも起きない。確定ではないが、方向としてはサブフォルダ寄り。

## デイリーノートでの配置

SRS ノートはデイリーノートの一番下に配置される。routine ノートが先に並び、SRS ノートはその後に来る。section（時間帯）が指定されている SRS ノートはその section の位置に入る。section なしの SRS ノートがすべての routine より後ろに来る。

## 1日の上限（srsMaxDaily）

`srsMaxDaily`（デフォルト 3）。デイリーノートに出す SRS ノートの1日あたり上限。due のノートが上限を超えた場合、next_due が古い順に上限件数だけ表示し、残りは翌日以降に繰り越される（next_due は書き換えない。表示しないだけで翌日も due のまま残る）。0 にすると無制限。routine ノートはこの上限の対象外で、常にすべて表示される。

### 過去のデイリーノートでの完了

6月25日 due のノートを 6月30日のデイリーノートで完了した場合、completionDay は 6月30日（デイリーノートの日付）になる。next_due は 6月30日 + repeat で計算される。overdue growth により、5日間の経過日数が考慮される。
