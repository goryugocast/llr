# System Architecture (システム構成)

## 1. Vault Structure (ディレクトリ構造)
```text
(Vault Root)
├── Daily work note        <--Current Workspace (legacy example: today.md)
├── routine/                    <--Routine Definitions (Master)
└── llrlog/             <--System Data (Current: routine/frontmatter only)
```

## 2. Core Components

### A. Day Boundary logic (日付境界・繰り越し)
**Status: Not Implemented**
- 指定された時刻（例: AM 4:00）を境界として、新しい一日を開始する。
- 実行時に現在のデイリーノート/作業ノートをアーカイブし、未完了タスクと今日のルーチンを新しく書き込む。

### B. Async Writer (非同期書き込み)
**Status: Out of Scope (Current)**
- JSONL等の外部ログ保存は現行仕様では実装しない。
- 実績の正は Markdown のタスク行とする。

### C. Discovery Logic (発展的紐付け)
- 構造の変化に追従するため、以下の3段階で判定を行う：
    1. **Explicit (@)**: 行内に `@[[routine/Name]]` があれば強制紐付け。
    2. **Implicit (Capture)**: タグや親フォルダから自動判定。
    3. **Learning**: ユーザーの選択を学習。

### D. Rebuild (再構築)
**Status: Not Implemented**

### 3.2 設計原則

- **純ロジックは `service/` に置き、Obsidian 依存（app / editor / metadataCache）から分離する。** 単体テスト可能性のため。`main.ts` / `view/` は Obsidian 依存のため統合テスト領域。
- **共有ユーティリティは一箇所に集約する。** 同一実装の重複（過去 `addDays` / `normalizeAsciiDigits` が yaml-parser と routine-engine に二重定義されていた）は非対称バグの温床。`yaml-parser` を日付/数字ユーティリティの単一の源とする。
- **Obsidian 内部 API への依存はキャスト境界（`as unknown as {...}`）に局所化する。** 公開型にない内部構造（`internalPlugins` / CM6 view 等）はバージョンで揺れるため、フォールバックを用意し局所化する。

### 3.3 品質ゲート

- リリース CI（`.github/workflows/release.yml`）は **型チェック（`npm run typecheck` = `tsc --noEmit`）→ lint → test → build** の順で実行する。esbuild は型を見ないため、型チェックを独立ステップとして必須化している。
- `tsconfig.json` は `noImplicitAny`、eslint は `no-explicit-any` 等を有効化。型エラー・lint 警告ゼロを維持する。
